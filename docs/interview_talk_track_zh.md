# 面试讲解稿：SQL 电商分析项目

## 60 秒版本

我用公开的 Olist 巴西电商数据做了一个端到端的 SQLite 项目。这个数据不是京东数据，所以我不会把结果说成京东的经营情况；我借用了平台型电商的分析框架，模拟商业分析和商家运营会问的问题。

我先把 customers、orders、order_items、products 和 sellers 建成关系型数据库，再把已送达订单定义为完成交易。为了避免一笔多商品订单被重复算作多个订单，我先在 CTE 里把 item 明细汇总到订单粒度，再做月度趋势、客户分层、商家排名和品类分析。

结果里我发现复购率只有 3.0%，而高价值的一次性客户贡献了约 61.5% 的商品金额，所以我提出优先做首购后的二购运营。商家侧，我用 `LAG()` 找到订单增长但商品金额没有同步增长的商家月份，建议进一步检查商品结构、价格和流量质量，而不是只看订单量。项目里还用 `RANK()`、`ROW_NUMBER()` 和累计窗口函数做商家集中度和诊断优先级排序。

我认为这个项目体现的是：我不仅会写 SQL，也会先定义指标口径、控制数据粒度，并把结果转化为可验证的运营动作。

## 面试官可能追问的问题

### 为什么不直接做京东数据？

京东真实交易数据不公开。我选择了 Olist 的公开关系型数据，因为它同时有订单、客户、商品和商家表，适合模拟平台电商环境。我会明确说明数据来源和局限，用京东商家运营的业务视角做可迁移的方法演示，而不把 Olist 的数值套到京东。

### 为什么只用 `delivered` 订单算商品金额？

商业结果需要建立在完成交易上，所以核心收入、客单价、复购和商家表现都以已送达订单为口径。取消、不可用、处理中订单仍然有价值，但更适合用来分析转化漏斗、履约和异常原因，不能混进完成交易指标。

### 为什么要先汇总到订单粒度？

`order_items` 的一行是一个商品明细，一笔订单可能有多行。如果直接 `COUNT(*)`，会把多商品订单重复算成多个订单。因此我先按 `order_id` 汇总商品价格，再统计订单数和客单价。这是这类多表电商分析最容易出错的地方。

### 高价值客户怎么定义？

在这个项目中，高价值是“已送达订单商品金额不低于全体客户平均值”的透明规则，同时用是否有两笔及以上完成订单区分复购。真实业务中我会和团队根据客户生命周期价值、毛利、品类和活跃度共同确定阈值，且会做敏感性分析。

### 订单增长但金额下降，说明商家经营变差了吗？

不能直接下结论。这只是一个优先诊断信号，可能来自低价商品占比提升、促销、价格变化或低质量流量。下一步应看 SKU 结构、价格、折扣、退货/取消、履约和流量数据，再判断是健康的规模增长还是客单价问题。

### 这些 SQL 技术分别解决什么业务问题？

| SQL 技术 | 项目中的用途 | 业务价值 |
|---|---|---|
| CTE | 把订单明细→订单金额→客户/商家指标拆开 | 保证口径清晰，方便复核和修改 |
| `LAG()` | 当前月与上月比较 | 识别趋势和异常变化 |
| `RANK()` | 商家/品类按金额排名 | 明确资源优先级 |
| `ROW_NUMBER()` | 给异常商家月份排诊断顺序 | 让运营团队能按优先级行动 |
| `NTILE()` | 找高销量、低价格品类 | 发现加购、捆绑和交叉销售候选 |

## 你可以主动强调的边界

- Olist 是历史公开数据，不是京东数据。
- 商品金额是 `SUM(price)`，不等同于平台 GMV、收入或利润；它不含运费、平台佣金、折扣和成本。
- 数据没有曝光、点击、库存、毛利或促销成本，所以项目不声称转化率或因果效果。
- 我把建议写成可以测试的假设，并说明需要补充什么数据来验证。
